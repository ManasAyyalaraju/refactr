# Decision Log

Why things are the way they are. Not a changelog of *what* changed (git history covers that) — this is for decisions that aren't obvious from reading the code. Append to this as new non-obvious decisions get made; no need to backfill every session, just the ones that would otherwise get re-litigated or re-derived from scratch.

---

**Backend is stateless; all Supabase access is frontend-driven.**
The FastAPI backend never gets a Supabase service_role key and never talks to Supabase directly — it only does OpenAI calls and LaTeX rendering. Auth, storage, and DB writes all happen from the Next.js app and the Chrome extension via `supabase-js`, protected by RLS. Chosen over a backend-owns-persistence approach because (a) the Chrome extension needs the exact same auth/storage pattern anyway — building it once in the browser-side client means the extension reuses it directly instead of duplicating logic across two different architectures, and (b) it keeps the backend's blast radius small: if Supabase has an outage, the core tailor/reformat functionality (talking to OpenAI, rendering PDFs) is unaffected.

**Rebranded JobCraft → refactr.**
Triggered by the user sharing a reference landing-page screenshot branded "refactr" — which turned out to exactly match their Supabase project's name/org, confirming it was an intentional rebrand rather than a one-off mockup.

**Technical Skills is a render flag, not a second template.**
`resume.technical_skills` (categorized `{label, items}` list) either renders as its own TECHNICAL SKILLS section or doesn't, controlled by a single `use_technical_skills` boolean passed into `render_resume_pdf()`. There's one LaTeX template, not two. The category structure mirrors the user's own real resume format (bulleted `Label: item, item, item` lines) rather than a fixed taxonomy, so parsing preserves whatever categories a given resume actually uses.

**A resume-fullness scoring bug had to be fixed alongside the Technical Skills feature.**
The heuristic that decides whether a resume is "full" (skip inventing a filler headline/summary) or "sparse" (add one) didn't know the new TECHNICAL SKILLS section existed, so it kept treating resumes as sparse even when that section alone was eating real page space. Fixed by giving `technical_skills` weight in `estimate_resume_fullness()`. Worth remembering if the threshold (35) ever needs retuning again — it's sensitive to *any* new section type being added without updating this function.

**Chrome extension: built fresh, not on top of the existing teammate branch.**
A teammate (vyomsethia) had already built a working prototype on `codex/build-chrome-extension` — but it was click-to-open (not auto-appearing) and fully anonymous (upload-a-PDF-every-time, no login). The target UX (auto-panel on job pages, logged-in with saved resumes) was different enough that starting clean was simpler than adapting it.

**Extension login is a full session handoff, not just a link to the web login page.**
A browser extension and a website are different security origins — they don't share cookies/localStorage, so opening the web login page alone wouldn't authenticate the extension. The extension has a stable ID (a fixed `key` in `manifest.json`, generated once from a throwaway RSA keypair — don't regenerate this without also updating `EXTENSION_ID` in `frontend/lib/extension.ts`) so the web app's `/extension/connect` page can reliably message it via `chrome.runtime.sendMessage` + `externally_connectable`, handing over the session tokens directly.

**`/tailor` moved from "upload a fresh file every time" to "pick from your saved resumes."**
Originally every tailor run re-uploaded the file as a new `base_resumes` row (creating duplicates on every use). Redesigned alongside adding a dedicated `/resumes/new` upload flow: `/tailor` now requires at least one saved resume and picks from `listBaseResumes()`, and persistence just links the existing `base_resume_id` instead of creating a new row each time.

**Every saved base resume gets reformatted before storage — never the raw upload.**
`/resumes/new` runs the uploaded PDF through `/api/reformat/pdf` (with the user's chosen Regular/Technical template) before saving the result to `base_resumes`. This normalizes every saved resume into the app's clean, consistent template from the moment it's added, rather than storing whatever arbitrary formatting the original file had.

**Template previews on `/resumes/new` are real PDFs, not mockup images.**
A hardcoded example resume ("Jordan Smith") renders through the actual `render_resume_pdf()` pipeline for both formats (`GET /api/templates/preview`), cached in memory since the content never changes. Chosen over static illustration images because it was nearly free to build (the rendering pipeline already existed) and is 100% accurate to what the user will actually get — no risk of the preview drifting from reality as the template evolves.

**Dashboard "current resume" = most recently saved, full stop.**
No `is_default` flag logic (the column exists in the schema but is unused) — just `base_resumes` ordered by `created_at desc`, first one is "current" and gets the big preview, the rest are a secondary list below it. Simplest model that matches how the upload flow actually works (every save on `/resumes/new` becomes the new current resume).

**Picking "Technical" only categorizes skills if the source resume doesn't already give us something to fall back on — needed an LLM assist.**
The parser was intentionally conservative: it only populates `resume.technical_skills` when the uploaded resume already presents skills in a "Label: item, item" categorized format (see the Technical Skills decision above), so a resume with a flat, uncategorized "Skills" list always came back with `technical_skills = []`. But the LaTeX template only renders the TECHNICAL SKILLS section when that list is non-empty, so selecting "Technical" on a flat-skills resume silently produced output indistinguishable from "Regular" — no error, just a no-op. Fixed by adding `categorize_skills()` in `llm_client.py` (small GPT-4o-mini call, same pattern as `generate_headline_summary`) and `ensure_technical_skills()` in `tailor_engine.py`, which buckets the flat `resume.skills` list into categories only when the Technical template is requested and no categories exist yet. Called from both `tailor_routes.py` and `reformat_routes.py` right before `render_resume_pdf`, gated on `use_technical_skills` so Regular-format requests never pay for the extra API call.

**Page-fit is verified by actually rendering and counting pages, not guessed from content heuristics.**
Dense resumes (many jobs, long bullet lists) could overflow to 2 pages even with `compact_mode`'s tightest existing spacing tier - and the categorized TECHNICAL SKILLS section makes this worse since it adds real content (a section header + one line per category) that a flat "Skills:" paragraph didn't cost. Two fixes, complementary:
1. Several spacing values (`\titlespacing*{\section}`, header/contact vspace, page margins) were hardcoded and never actually responded to `compact_mode` despite that mechanism existing for exactly this purpose - only `entryvspace`/`sectionvspace` did. Wired all of them into the existing compact/non-compact toggle in `resume_template.tex`.
2. For the remaining cases still too dense even at full compact spacing: `render_resume_pdf()` in `pdf_writer.py` now renders once, counts the actual output pages via PyPDF2, and only if it's still >1 page does it re-render once with a new `ultra_compact_mode` flag (`Resume.ultra_compact_mode`) that nudges the font down slightly (`\fontsize{9.3}{11.3}`). This only ever fires for resumes that actually overflow - measured, not predicted from a threshold - so it never touches resumes that already fit fine at normal or compact spacing.
Also reordered both `tailor_routes.py` and `reformat_routes.py` to call `ensure_technical_skills()` *before* tailoring/reformatting (which is where `compact_mode` gets computed from resume content) instead of right before rendering - so the fullness/compact-mode decision actually sees the technical-skills section that's about to be added, rather than deciding spacing based on a resume that's about to grow.

**Short wrapped-bullet trailing lines are fixed with typography, not by padding bullet text with extra words.**
User flagged that a bullet wrapping to a 2nd line often left that line looking sparse (e.g. just "reach 50K+ users at launch"). The tempting fix - have the AI add a few filler words - was ruled out for the Reformat flow specifically, since that flow's whole value proposition is preserving bullets **verbatim** from the original resume (see the reformat-engine entry above); inventing wording there would break that guarantee. Settled on a typography-only fix instead, since it applies safely to both Tailor and Reformat: `\usepackage[USenglish]{babel}` (proper hyphenation patterns - previously the template had none) plus `\usepackage[stretch=25,shrink=25]{microtype}` (font expansion/protrusion) plus raising `\tolerance` from 500 to 2000, all in `resume_template.tex`. Higher tolerance lets LaTeX's line-breaker stretch a fuller line rather than reflexively wrapping a word down early, which pulled real content up onto the first line in testing (the 50K+ example above gained "projected to" on its second line, no wording changed). This has a mathematical ceiling - a bullet whose content is inherently ~1.1 lines will always leave *some* short remainder, since that's a direct function of character count vs. column width, not a rendering defect - so don't expect every wrap to look perfectly full.

**Setting `urlcolor=black` alone didn't make the LinkedIn link black - the real bug was a missing URL scheme.**
Vyom's resume had `contact.linkedin` parsed as `linkedin.com/in/vyomsethia` (no `https://`, since that's how it appeared in his original resume). hyperref's `\href` only classifies a target as a "URL" link (governed by `urlcolor`) when it recognizes a scheme; without one it falls back to treating it as a **local file** link, which isn't covered by `urlcolor`/`linkcolor` at all - so it kept rendering in hyperref's uncustomized default color regardless of what `\hypersetup` said. Worse, this isn't just cosmetic: most PDF viewers would try to open a local file named `linkedin.com/in/vyomsethia` on click rather than launching a browser, silently breaking the link. Fixed at the root with a new `ensure_url_scheme()` Jinja filter in `pdf_writer.py` that prepends `https://` when a URL has none, applied to both the contact LinkedIn link and Publications URLs in `resume_template.tex` (display text stays as originally written; only the `\href` target gets the scheme). Also added `filecolor`/`citecolor` to `\hypersetup` as a belt-and-suspenders fallback so no link category is ever left uncustomized. Lesson: when a color/style setting "isn't taking effect," check whether the content is even hitting the code path that setting controls before assuming the setting itself is wrong.

**Personal website/portfolio links were silently dropped - `Contact` had no field for them.**
Manas's resume has "manasayyalaraju.com" in the header alongside email/phone/LinkedIn, but the `Contact` pydantic model only had `email`, `phone`, `linkedin`, `location` - so the parser had nowhere to put a website URL and it just vanished, with no error anywhere since it's not a validation failure, just a schema gap. Added `contact.website` across the full chain: `resume_models.py`, the parser prompt in `pdf_resume_parser.py`, trimming in `reformat_engine.py`, and rendering in `resume_template.tex` (reusing the `ensure_url_scheme` filter from the LinkedIn color fix, so a bare "manasayyalaraju.com" gets a proper `https://` scheme for correct link color/click-through). Rendered order in the contact line: email · phone · website · linkedin · location.

**Technical Skills categorization can drift between runs on the same resume - not something to "fix" by force, since it's downstream of GPT sampling, not a rendering bug.**
While debugging the website field, noticed that re-parsing the *same* PDF twice produced different results: once correctly picked up the original's 3 hand-written categories ("Computer Software", "Computer Languages", "Certifications"), another time came back with `technical_skills: []` (likely because this particular resume's raw PDF-extracted text has odd spacing artifacts like "Software :" and "Power B I", which occasionally confuses the categorization detection), which then triggered `ensure_technical_skills()` to auto-invent a *different* set of categories from the flat skills list. Both outcomes are individually "correct" per their own logic, but produce visibly different resumes from the same input, which would look like nondeterministic/buggy behavior to a user reformatting the same resume twice. Not fixed yet - flagging here since the fix (e.g. making the parser's categorized-skills detection more robust to spacing artifacts, or making `ensure_technical_skills` deterministic/cached per input) needs its own pass, not a drive-by change.

**`categorize_skills()` was over-classifying - settled on dynamic-but-broad, not a fixed taxonomy.**
The original prompt let GPT invent whatever categories it wanted ("2-5 clear categories"), which produced inconsistent, overly-granular results per resume - e.g. one run split a single person's skills into "Web Development", "Data Science", "Databases", "Business Intelligence", and "DevOps & Tools", and even miscategorized certifications ("AWS Certified Cloud Practitioner") as a DevOps tool rather than a credential. First fix tried a hardcoded 3-label taxonomy ("Computer Languages" / "Computer Software" / "Certifications"), but the user pushed back - they like category labels that adapt to the resume's actual content (e.g. "Design Tools" fits a designer better than a generic "Software" bucket), just want FEWER, BROADER ones instead of many narrow ones. Landed on a hybrid: category labels are still chosen dynamically by the model per-resume, but the prompt in `llm_client.py` now hard-caps it at 2-4 categories total and explicitly instructs "merge related skills into the same broader category instead of creating a new one" - with certifications/credentials always kept as their own separate category when present (never folded into a technical-skills bucket, and never omitted). This also fixes a visible duplication: once certs land in a real "Certifications" category, `_dedupe_additional_info_against_technical_skills()` in `pdf_writer.py` (existing logic) correctly clears the redundant `additional_info.certifications` list at render time instead of showing certs twice. One more follow-up: labels like "Web Development & Programming" were still eating line width, so the prompt now also caps each label at 1-2 words / a single concept and explicitly forbids "X & Y" compound labels - e.g. "Data & Analytics" became "Data Analysis".

**Don't trust a reported Supabase Auth setting without checking the data.**
Early on, "Confirm email" was reported as OFF, but a real signup showed `email_confirmed_at: null` — i.e. it was actually ON. The signup flow was built to handle both cases correctly regardless (immediate session vs. deferred display-name application on first login), rather than branching on which setting was assumed to be true.

**`extension-release` doesn't auto-update from `master` - rebuilding and pushing it is a manual step, kept manual on purpose.**
The public download link (`/extension` page, GitHub's `archive/refs/heads/extension-release.zip`) always serves whatever `extension-release` currently points to - GitHub generates that zip live per request, so the *link* itself never goes stale. But changes to `extension/src/*.ts` or `extension/manifest.json` on `master` do NOT propagate to `extension-release` on their own. After any extension change: rebuild (`cd extension && npm run build`), then push the fresh `dist/` output to `extension-release` (a temporary `git worktree` of that branch works well - replace the built files, commit, push, remove the worktree). Skipping this step is exactly what caused a real bug: `extension-release` was last built before the `refactrapp.com` custom-domain migration, so the "Log in to refactr" button kept opening a dead Vercel URL until it was manually rebuilt and pushed. A GitHub Action could automate this (rebuild+push on every `extension/` change to `master`), but the user chose to keep it manual for now rather than add that automation.
